# CiteCiter 产品规则

本文记录 CiteCiter 现行的产品规则。新功能和修改应遵守这些规则；规则本身需要改变时，先更新本文。

## 定位

CiteCiter 帮助用户从真实的 Agent 工作中获得理解与判断。首要用户是已经用 Agent 完成了真实任务，却在解释、维护或验收成果时发现自己缺少理解的人。用户从主对话、工具结果、文件预览或导入的文档中选取疑问，在独立 Topic 中追问、绘图或整理学习卡，再回到原任务。

学习理解是首要场景，Topic 同样支持普通问答、编程与图像任务。权限、模型调用、工具执行、排队、插话、停止和审批都复用 DSH 的原生能力。

## 发送与草稿

- 模型只在用户明确发起时运行：手动发送，或选择一个预设动作（设置中可以改为只放进输入框）。创建 Topic、选择“提问”、点击建议追问或引用板书都只准备草稿。
- 直接发送的预设动作作为一条独立的用户消息排队，带上选文的来源与摘录，不改动输入框里已有的草稿。宿主明确拒绝时（例如模型不可用），这条动作放回输入框；无法确认是否发出时只提示用户核对，不重复发送。
- 来源地址、原文摘录、文档地址和板书引用是可移除的草稿附件。未发送的附件不进入模型输入，也不授予来源读取权限；已发送的历史不会因为删除后续草稿中的副本而撤回。
- 草稿的文字、引用和附件字节持久保存。宿主确认接收后只清除这一次提交的内容，保留提交期间新增的编辑。刷新和重启不会自动发送。
- 多个窗口的草稿修改自动合并，同一处冲突以正在操作的窗口为准，界面不显示保存进度或版本选择。保存或附件恢复失败必须明确提示，并保留可恢复的内容。
- 未提交的问答（问题卡）与普通草稿分开保存。宿主退出中断的问答在原 Topic 恢复，等待用户手动补答；明确取消或停止的问答不再恢复。

## Topic、来源与存储

- 每个来源会话目录下的 `citeciter/` 由 Citer 管理，Topic 的日志、草稿、归档和删除都限定在其中。Citer 不向主会话写入任何内容，Topic 也不出现在 DSH 的会话列表里。
- 所有动作默认加入当前来源中选中的未归档 Topic；没有选中或当前 Topic 已归档时新建。要另开 Topic 时，用户在工具条菜单中选择“在新 Topic 中提问”，或先在面板中新建。追加时保留已有草稿、模型和权限。
- 归档保留完整记录；在归档 Topic 中手动发送并被宿主接受后，它回到活动列表。工具结果和模型回答本身不改变归档状态。
- 永久删除需要输入完整 Session ID，只删除该 Topic 的日志、草稿、问答草稿、附件和代码库快照，留下只含身份与清理状态的删除记录。来源会话、其他 Topic 和迁移备份不受影响。
- 每个 Topic 都知道自己所在的来源会话：系统提示词写明来源会话 ID，Citer 随时可以用读取工具读它，不需要先发送来源附件，也不能读取其他会话。Citer 以带位置标记的 Markdown 对话记录读取来源，默认缩短过长的工具内容，并能按位置重读全文。自动附上来源摘录默认关闭；开启后于每轮开头附上来源最近的新内容。
- 代码库变化感知在每轮开头告诉 Citer 上一轮开始以来 git 工作区的变化，默认只列文件清单，由 Citer 按需用工具读取逐行改动；用户可以改为直接附上 diff 或关闭。快照存放在 Topic 自己的目录中，使用独立的 git 对象库，不写入用户仓库。
- Citer 每轮附加的上下文作为带来源的消息写入 Topic 日志，不放进会随时间变化的系统提示词。这些消息使用 DSH 定义的上下文形式（代码库变化是带摘要的通知，来源摘录是召回），Topic 像 DSH 的对话一样显示这些通知和召回，展开即是模型收到的原文；运行环境、时间等普通上下文默认不列出，用户可以在 Topic 菜单中选择显示。失败和停止记录保留在历史中。
- 会话日志格式由 DSH 管理。Citer 不手工改写或降级日志；旧版本的数据通过 DSH 公开的持久化接口迁移，逐条核验后才切换，原始文件保留。

## 权限与模型

- 新 Topic 默认只读，即使来源会话拥有更高权限。用户主动选择其他权限模式或修改新 Topic 的默认值后才允许对应操作，DSH 的审批、沙箱和工具限制继续生效。
- 模型菜单先选模型，再选它支持的思考强度。新 Topic 使用设置中的模型，未设置时继承来源会话当前选择的模型（即来源输入框里显示的模型，而不是上一次实际运行的模型）。这个模型在当前 DSH 中不可用时（例如设置来自另一台机器），仍然创建 Topic、保留引用和草稿并提示用户选择，不自动替换模型或发送。
- 图像生成和查看由宿主插件提供（例如社区插件 Codex Connect）；工具不可用时如实说明，Citer 不代替实现。
- 新 Topic 先以引用摘录或问题为标题，第一次运行时由 DSH 自带的标题服务生成摘要标题；用户重命名后不再自动修改。

## 交互与学习

- 在主对话（助手回答、用户消息、工具结果）、文档或 Citer 自己的回答中选中文字后出现工具条：第一个动作（默认“问 Citer”）之后是固定的“引用”，然后是接下来的三个动作，其余动作和“在新 Topic 中提问”在“⋯”菜单中。工具条不接管浏览器的右键菜单，也不改变选区。
- “引用”只准备草稿，不发送。在主对话中选文时，它是主对话输入框里的一个 DSH 原生引用胶囊，加在末尾，不改动已有文字和附件，光标随后落在它之后。发送时主 Agent 收到 `<quote from="assistant|user|tool">原文</quote>`：只有原文一字不改和说话方，不加解释或指令；宿主支持时，已发送的消息把它显示为胶囊。在 Topic 中选文时作为引用附件加入这个 Topic 的输入框。
- 文档只有一种阅读方式和一种提问方式：在 DSH 右侧栏的标签页（不使用右侧栏时是 Citer 面板的页签）里连续阅读，选中文字后用同一个工具条提问，不另设提问框。Markdown 按 DSH 的样式排版，文本和代码带行号。导入的文档存放在 Citer 自己的文档库中，原样保存、不再改动；工作区文件由 DSH 的文件预览打开，Citer 只提供一种阅读视图，提问时才把当时的内容存为快照。选区由宿主在原文中重新定位：Markdown 选区只在所选段落的原文内匹配，因此同一句话出现多次时不会认错位置；从文档提问的 Topic 显示文档名和起始行，并能回到原文那一段。删除文档只移除文档本身，相关 Topic 的对话保留。
- 轮盘是可选手势，默认关闭；开启后按住触发键使用同样的八个动作。
- Citer 收起时以桌宠停靠在窗口左边或右边：平时扒着窗口边缘探头，鼠标靠近或获得焦点时站起来，点击打开 Citer，可以拖到任意一侧并记住位置。面板收起期间有回答完成或问题卡等待时，桌宠旁显示提示点。
- 输入框依次提供附件、权限模式、模型与思考强度和发送。Enter 发送，Shift + Enter 换行，输入法组词时不提交；生成中跟随 DSH 的排队／插话设置，Ctrl + Enter 临时切换。
- Citer 是 DSH 右侧栏中的一个标签页，和文件、终端、其他插件的标签一样由 DSH 负责分屏、悬浮、全屏和关闭；侧栏的指引页提供 Citer 入口。用户可以在设置中选择不使用右侧栏，此时所有入口都打开 Citer 自己的面板，侧栏里的 Citer 标签会交给这个面板。宿主没有右侧栏或用户不使用它时，Citer 使用自己的面板：宽窗口中与主对话并排，窄窗口中以带返回键的独立页面显示。
- 界面文字跟随 DSH 的语言设置，通过 DSH 的语言服务注册词典，语言包插件可以为 Citer 增加语言。默认动作的名称和提示词随语言切换；用户保存过的动作保持原样。来自宿主运行时的少数提示和模型可见的协议标记不翻译。
- Topic 在输入框下方显示自己的用量：token 总数、缓存命中率和上下文占用，与 DSH 输入框下方的统计一致。
- 学习路线默认关闭。开启后由模型通过 DSH 待办选择必要的讲解阶段，用户指定的范围、篇幅和卡片数量优先。
- 学习卡可以单独请求。生成前要求模型在同一轮中核对结论、计算和示例；自查不等于独立验证。主动回忆可选且默认关闭，不安排间隔复习或提醒。
- 板书只有一个入口。支持视觉的模型通过实际渲染的截图检查板书，不能把只读取绘图参数当作视觉检查。黑板保持深色画布，模型按此选择颜色，已保存的板书依赖这一点。
- 板书动画建立在已画好的元素上：模型用动作、关键帧、路径或受限的数学表达式编排一条时间轴，不执行脚本。播放、暂停、拖动和按步骤跳转由用户控制；关闭板书动画或系统要求减少动态效果时停在最终帧，不能播放；用户仍可拖动进度或按步骤查看单帧静态画面。模型通过指定时刻的截图检查关键帧。
- 界面与 DSH 保持一致：使用宿主的颜色、字号、圆角、分隔线和控件，不加装饰性的底色或说明文字。界面中的名称是 Citer；角色形象只用于标识（标题栏、空状态、设置页和收起时的桌宠）。

## 工程原则

- 遵循 [DSH 的插件规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md)：行为放在插件和公开的扩展点上，不修改宿主的 Agent Loop；模型能看到的内容都能从会话日志重建。
- 必要的宿主适配集中在独立模块中并写明原因，不扩散到其他代码。
- React 组件只接收状态和业务回调，不自行查找 Cordis 服务。
- 静态检查和单元测试不代替真实使用；用户可见的改动需要在真实 DSH 中用真实模型验证。模型的回答流畅不代表事实正确。

## 后续方向

优先收集可以核对的使用案例：用户能否解释一个关键选择、发现一个遗漏的问题，或在下一次相似任务中做出更好的判断。先验证理解上的收益，再决定推广范围和支持的宿主。

"深入核验"模式是一个可能的方向：默认关闭，由需要的用户主动开启，组织证据、反例、边界条件或小实验；日常讲解保持轻量，并如实说明不确定性。
