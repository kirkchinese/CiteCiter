# CiteCiter 产品规则

本文记录 CiteCiter 现行的产品规则。新功能和修改应遵守这些规则；规则本身需要改变时，先更新本文。

## 定位

CiteCiter 帮助用户从真实的 Agent 工作中获得理解与判断。首要用户是已经用 Agent 完成了真实任务，却在解释、维护或验收成果时发现自己缺少理解的人。用户从主对话、工具结果、文件预览或导入的文档中选取疑问，在独立 Topic 中追问、绘图或整理学习卡，再回到原任务。

学习理解是首要场景，Topic 同样支持普通问答、编程与图像任务。权限、模型调用、工具执行、排队、插话、停止和审批都复用 DSH 的原生能力。

## 发送与草稿

- 只有用户手动发送才启动模型。创建 Topic、选择轮盘动作、点击建议追问或引用板书都只准备草稿。
- 来源地址、原文摘录、文档地址和板书引用是可移除的草稿附件。未发送的附件不进入模型输入，也不授予来源读取权限；已发送的历史不会因为删除后续草稿中的副本而撤回。
- 草稿的文字、引用和附件字节持久保存。宿主确认接收后只清除这一次提交的内容，保留提交期间新增的编辑。刷新和重启不会自动发送。
- 多个窗口的草稿修改自动合并，同一处冲突以正在操作的窗口为准，界面不显示保存进度或版本选择。保存或附件恢复失败必须明确提示，并保留可恢复的内容。
- 未提交的问答（问题卡）与普通草稿分开保存。宿主退出中断的问答在原 Topic 恢复，等待用户手动补答；明确取消或停止的问答不再恢复。

## Topic、来源与存储

- 每个来源会话目录下的 `citeciter/` 由 Citer 管理，Topic 的日志、草稿、归档和删除都限定在其中。Citer 不向主会话写入任何内容，Topic 也不出现在 DSH 的会话列表里。
- "自由提问"把选文追加到当前来源中选中的未归档 Topic；没有选中或当前 Topic 已归档时新建。其他内置动作默认新建，自定义动作可以设置目标。追加时保留已有草稿、模型和权限。
- 归档保留完整记录；在归档 Topic 中手动发送并被宿主接受后，它回到活动列表。工具结果和模型回答本身不改变归档状态。
- 永久删除需要输入完整 Session ID，只删除该 Topic 的日志、草稿、问答草稿和附件，留下只含身份与清理状态的删除记录。来源会话、其他 Topic 和迁移备份不受影响。
- 会话日志格式由 DSH 管理。Citer 不手工改写或降级日志；旧版本的数据通过 DSH 公开的持久化接口迁移，逐条核验后才切换，原始文件保留。

## 权限与模型

- 新 Topic 默认只读，即使来源会话拥有更高权限。用户主动选择其他权限模式或修改新 Topic 的默认值后才允许对应操作，DSH 的审批、沙箱和工具限制继续生效。
- 模型菜单先选模型，再选它支持的思考强度。继承的模型已经不可用时，保留 Topic 和草稿并提示用户选择，不自动替换模型或发送。
- 图像生成和查看由宿主插件提供；工具不可用时如实说明，Citer 不代替实现。

## 交互与学习

- 轮盘有八个槽位，选择动作后直接进入 Citer 输入框，用户可以调整文字、引用、模型和权限后再发送。
- 输入框依次提供附件、权限模式、模型与思考强度和发送。Enter 发送，Shift + Enter 换行，输入法组词时不提交；生成中跟随 DSH 的排队／插话设置，Ctrl + Enter 临时切换。
- 宽窗口中主对话与 Citer 并排；窄窗口中 Citer 以带返回键的独立页面显示。空间不足时新打开的原生文件详情优先，Citer 暂时收起并保留草稿。
- 学习路线默认关闭。开启后由模型通过 DSH 待办选择必要的讲解阶段，用户指定的范围、篇幅和卡片数量优先。
- 学习卡可以单独请求。生成前要求模型在同一轮中核对结论、计算和示例；自查不等于独立验证。主动回忆可选且默认关闭，不安排间隔复习或提醒。
- 板书只有一个入口。支持视觉的模型通过实际渲染的截图检查板书，不能把只读取绘图参数当作视觉检查。

## 工程原则

- 遵循 [DSH 的插件规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md)：行为放在插件和公开的扩展点上，不修改宿主的 Agent Loop；模型能看到的内容都能从会话日志重建。
- 必要的宿主适配集中在独立模块中并写明原因，不扩散到其他代码。
- React 组件只接收状态和业务回调，不自行查找 Cordis 服务。
- 静态检查和单元测试不代替真实使用；用户可见的改动需要在真实 DSH 中用真实模型验证。模型的回答流畅不代表事实正确。

## 后续方向

优先收集可以核对的使用案例：用户能否解释一个关键选择、发现一个遗漏的问题，或在下一次相似任务中做出更好的判断。先验证理解上的收益，再决定推广范围和支持的宿主。

"深入核验"模式是一个可能的方向：默认关闭，由需要的用户主动开启，组织证据、反例、边界条件或小实验；日常讲解保持轻量，并如实说明不确定性。
