## 用户原始目标

> 重提此插件的简单目标：基于 DeepSeek Harness（DSH）好用好看的，的学习伴侣插件——让你在 AI 工作过程中就任意一段中选中文字，右键点 `Citer!`，就你没看懂的部分多轮追问 AI直到完全弄明白为止。
>
> 要解决的核心问题：AI 回答得太快、看起来什么都会，用户容易一边点头一边错过真正理解的机会。CiteCiter 的目的不是“再问一遍 AI”，而是在精确的历史边界上帮你追上AI吐出的内容，不成为只被AI牵着鼻子走的操作工。
>
> 我希望能够以“模型调用”为最小单元组织会话。由于真实使用中人们往往让DS执行长程任务，而人在监控中就会发现不懂和存在问题的地方，他们需要一组“发现疑似问题->询问->确认或抛弃问题->修正方向”的循环，等待每一轮结束就太晚了。真实的使用中人们实际不只把他当作一个解释助手，而是一个随时可以呼唤出来问询问题的随身秘书。为满足人们的需求，我们需要提供更好的设计。
>
> 我认为citeciter应该自行管理自己的对话数据，但应该保持对官方对话的支持，因为上游不会为你让路，而你需要适配官方。自行管理还有好处，这让我们的开发不必被官方可能随时变化的接口弄得疲于奔命。
>
> 过于依赖主对话，UI、导航和 Thread 组织不应该继续暴露为普通 DSH 子会话。我有个想法，提供可选择配置，第一个是现在的模式，直接继承上下文回答。另外一种是以旁观者视角，直接告知模型目标session文件位置并要求生成回答。这两种可供用户自行选择，并告知区别。我们测试效果后确定默认模式。

## 第一轮问答

### 1. 最小可引用边界

问题：一次 DSH `step` 包含模型请求和随后执行的工具。正式 Citation 应在 `assistant/message` 完成、整个 `step/end` 完成，还是流式文本尚未完成时即可创建？“模型调用”是可引用证据单元，还是必须物理 fork 一个会话？

用户回答：

> A 以模型调用作为可引用的最小单元

确认：提交后的 `assistant/message` 是正式 Citation 的最小边界，不要求来源轮次结束，也不要求每次模型调用都物理 fork。

### 2. 是否回写来源 Agent

问题：用户通过 CiteCiter 判断主 Agent 可能出错后，CiteCiter 是否提供建议、回写或自动干预？

用户回答：

> A 始终只读，且citer不主动提建议，用户随便怎么和citer聊天，聊完之后他觉得主Agent做错了的话，怎么纠正是他自己的事情。我们不做干涉。我举的是个例子，我们只做基础设施，用户的用法是用户的事情。

确认：CiteCiter 始终只读，不主动评估或干预来源 Agent。用户如何使用讨论结果不属于插件职责。

### 3. CiteCiter 自主管理数据的范围

问题：CiteCiter 是只管理产品元数据并继续使用 DSH 对话运行时，还是连完整消息运行时也独立实现？

用户回答：

> 类似这种结构：.dsh/<project>/citer_session/<session>主要是不希望我们的citer对话和主要对话混在一起，干扰主要功能的使用。对于citer，他仍然继承dsh的所有技术标准，举个极端例子，用户找到了citer的session文件，他甚至可以通过手动修改有限的几个配置就让citer session出现在主要对话列表中。

确认：CiteCiter 使用独立的存储目录和目录索引，但每条对话仍是符合 DSH 规格的 Session；不重新实现模型流式、工具、压缩和回放标准。

### 4. Observer 的来源更新方式

问题：来源上下文是首问时冻结、每轮自动更新，还是默认冻结并由用户手动刷新？

用户回答：

> 对于这个问题，我有一个手动流程，请查看位于Drone_3D-01下名为'读取DSH会话记录汇报'的对话，这个Agent的流程就是我希望的，整个session是独立的，用户甚至可以提出题外话。接近第二种

确认：CiteCiter 是绑定来源的独立 Observer Session。用户问题涉及来源时，Tutor 读取来源的最新状态；题外话仍作为普通聊天处理。

### 5. Observer 可读取的来源信息

用户回答：

确认：来源读取覆盖用户消息、助手正文、工具调用和结果、可配置的 reasoning，以及来源工作区的只读文件。

## 冲突消解与最终解释

“Topic” 的最终定义以第 16 题为准：Topic 是一条具有 AI 生成标题的 CiteCiter 对话，一条 Topic 对应一个标准 DSH Session。

第 10 题选择 C 不再解释为“一个 Topic 内默认建立多个引用子主题”。第 14、15、16 题共同确定主流程：每次从选区浮层提交问题都会创建新 Topic；插件不自动复用旧讨论，也不要求用户把新 Citation 加入当前讨论。

一个来源 Session 对应一个 Companion Workspace。Workspace 只是 Topic 的分组和导航范围，不是模型对话或 DSH Session。

来源读取工具取代“把物理文件路径交给模型”。磁盘中的 CiteCiter Session 仍遵循 DSH Session 格式；路径隔离是产品目录和发现策略，不是另造聊天协议。

## 最终已确认需求

- CiteCiter 是只读学习伴侣基础设施，不是主 Agent 的监督器、评审器或控制器。
- 正式 Citation 的最小来源单位是已提交的 `assistant/message`，不等待来源 `turn/end`。
- Observer 是默认主流程；Tutor 在来源相关问题上按需读取最新 Session 证据。
- Exact Fork 是高级、冻结的历史模式，只能使用 DSH 接受的轮次间边界。
- 每条来源 Session 拥有一个 Companion Workspace；每次浮层提问创建一个新数字 Topic。
- Topic 标题由独立 AI 标题流程生成，用户只输入问题；旧 Topic 从 CiteCiter 侧栏恢复。
- CiteCiter Session 与主 Session 分开存放和索引，但日志、模型配置、工具、压缩和回放遵循 DSH 标准。
- CiteCiter 创建时复制来源模型配置，随后允许用户独立切换模型与思考强度。
- 来源读取包含用户消息、助手正文、工具调用和结果，以及默认启用但可关闭的来源 reasoning。
- CiteCiter 可通过标准只读文件工具读取来源工作区；任何操作都不能修改来源 Session、工作区或外部状态。
