# Retire local carriers after confirmed Topic deletion

Date: 2026-10-07. Scope: the Client that receives a successful, identity-checked CiteCiter deletion response. Targets remain official DSH Desktop 0.2.0-rc.2 and Web SDK 0.2.1-alpha.1; community desktop records are not evidence.

Read-only lifecycle review found that `createNativeComposer()` retained every opened `CiterSessionFace` in its `sessions` Map until plugin teardown. The permanent-delete path cleared question controllers but did not retire the corresponding face. Unmounting `NativeQueue` correctly removed its subscription, and a face with no pending submissions stopped polling; ordinary idle deletion therefore retained memory without necessarily retaining an active poll.

The additional pending-submission path is reachable from the code. `CiterSessionFace.beginSubmission()` registers a submission before the native prompt is sent; a successful prompt response schedules observation but does not retire it. `readNativeState()` recognizes a durable inbox insertion or user message as its receipt, and the Client retires the submission only after receiving that state. Neither the Topic settings button nor the Host delete operation prohibits deletion during this interval: the Host cancels and disposes the owned Agent. If deletion commits before the Client observes the receipt, subsequent state reads fail and the pending entry keeps the approximately 350 ms polling loop alive. Native DSH attachment sends also wait for the retirement callback, so that continuation could remain unresolved. A second window can cause the same ordering while the first window is waiting for its receipt. This is a source-level reachability finding, not a newly observed real-model deletion test.

The minimal repair adds `NativeComposer.retire(sessionId)` and calls it only after the local deletion response has been checked against the requested Session, source and Topic identities. Retirement removes and disposes the face and all question controllers for that exact Topic. A retired-identity set prevents stale callbacks from creating another local carrier for the deleted Topic; it contains only deletion identities confirmed by this Client and is cleared on plugin teardown. Attachment creation rechecks retirement after its asynchronous binding, and attachment retry rejects a retired Topic before invoking the Host. `CiterSessionFace.dispose()` is explicitly idempotent, aborts in-flight reads, clears its timer and prepared request identity, settles remaining native submission callbacks once with the existing failed outcome, and marks its final snapshot removed. No Host permission, Agent Loop, submission acceptance rule or log content changes. Temporary read failures still retain the existing retry behavior and are never interpreted as deletion.

Cross-window deletion is still an open engineering item. `citeciter/topic-deleted` is currently a Host-only Cordis event; the Client has no authoritative deletion subscription. This change deliberately adds no Remote API and does not infer deletion from a missing active-list entry, a generic not-found error or a transient transport failure. A complete follow-up needs an authoritative deletion channel plus durable deletion evidence for disconnect/reconnect recovery, rather than only a transient notification. Until then, another already-open Client can retain the old face and pending state when a different window deletes the Topic. This partial repair must not be presented as complete multi-window acceptance or release readiness.
