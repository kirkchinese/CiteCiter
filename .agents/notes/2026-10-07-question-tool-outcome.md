# Preserve official user-question cancellation outcomes

Date: 2026-10-07. Scope: official DSH Desktop 0.2.0-rc.2 acceptance, with Web SDK 0.2.1-alpha.1 compilation coverage. Community Desktop is outside the support and evidence scope.

Real-model acceptance found a presentation defect: answering an `ask_user_question` succeeded, and cancelling the following question correctly closed the card and let GPT-6-Sol answer “已取消”, but Citer's collapsed tool row said “调用失败”. The native result preserved `error: { name: 'UserQuestionError', code: 'ASK_CANCELLED' }` with `isError: true`; the Citer normalization discarded that structured code. Official DSH's `ask-question-row.tsx` distinguishes the user's cancellation from an aborted wait and an ordinary tool failure.

`tool-events.ts` now accepts only the two known structured `UserQuestionError` codes, `ASK_CANCELLED` and `ASK_ABORTED`, for presentation. It never guesses from the human-readable result text. Direct tool results and PTC child results use the same normalization. The strict Topic wire schema accepts this optional finite code, and `topicMessages()` carries it from durable events into both live settlement snapshots and restored history. Original `isError`, result content and Session log events are unchanged.

`ToolMessage.tsx` displays “已取消” or “已中断” only for an `ask_user_question` error with the corresponding recognized code, with a neutral “状态” detail heading. Every ordinary error still displays “调用失败”. Old rows without the optional field retain their existing rendering. No permission, source-reading, model-request or question lifecycle behavior changes.

Evidence: the acceptance source is `session-34316b58-111a-4f71-a2db-3922e57d7446`, Topic 1, with private Session `citeciter-7e1db1b4-35f6-4ad0-b2a5-09c9d51ffba1`. The successful answer is tool result sequence 16; cancellation is sequence 31, followed by a completed turn. Source log SHA-256 remained `c5fc3797df6c72537f93c44a782488111a45467f3ecbbaf7e4ca823a1285ed67` during both actions.

An inline protocol check against those actual durable events passed: recognized cancellation, successful answer, rejected unknown or malformed error taxonomy, PTC and historical envelopes, unchanged input events, strict wire validation and compatibility with rows lacking the new optional field. A second inline check ran `topicMessages()` against the real complete log and its pre-result prefix: the row remains running before settlement, then restores the cancellation code with `isError: true`, without an active failure banner. No test file or model substitute was created.

The shared outcome constants and type live in `tool-outcome-contract.ts`, which imports neither Host nor Client services. An initial implementation imported the constant from the Host-oriented `tool-events.ts` into `topic.ts`, accidentally pulling Host Context declarations into the Client type graph and making the correct Client `sessions.binding()` appear invalid. The constant was moved to the pure contract; the source Chat adapter uses a direct `ISessions = ctx.sessions` assignment without a cast. No Host/Client type conflict should be hidden by casting through `unknown`.

After the contract correction, `pnpm typecheck` and `pnpm typecheck:desktop` passed for both Host and Client. A direct TypeScript program inspection also confirmed that the Client source graph includes `tool-outcome-contract.ts` and excludes `tool-events.ts`; the real cancellation and wire-schema checks still passed. Candidate `fef557835beb` was subsequently installed and the official Desktop restarted: the restored cancellation row displayed “已取消”. A new real question was stopped while awaiting an answer; native result sequence 60 recorded `ASK_ABORTED`, sequence 62 ended the turn with `aborted/user`, and the UI closed the form and displayed “已中断” with a resumable stopped state. The source log remained unchanged by the Topic operations. These observed paths passed; real PTC cancellation and the complete acceptance matrix remain separate checks.
