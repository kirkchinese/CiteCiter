# Durable Topic deletion evidence

Date: 2026-10-07. Scope: independent deletion-receipt storage and `TopicIndex`; runtime and Client integration are separate. Targets remain SDK 0.2.1-alpha.1 and official Desktop SDK 0.2.0-rc.2. No community desktop record establishes acceptance.

The already identified cross-window lifecycle gap cannot be safely resolved by treating a missing Topic, an absent list entry or a transport failure as a deletion. Existing `deleting.json` markers establish a committed removal while cleanup is pending, but successful cleanup previously removed the only persistent evidence. A disconnected Client or a restarted Host consequently had no reliable way to distinguish a deliberately deleted Topic from a temporarily unavailable one.

`TopicDeletionReceipts` is a Host-only filesystem module without Agent or Client dependencies. Completed deletions retain exactly `version`, `sourceSessionId`, `topicId`, `sessionId` and `cleanup` in `<source>/citeciter/deleted/<sessionId>.json`. The record is an internal deletion receipt; it retains no message, draft, attachment or Session header. Topic content cleanup remains unchanged, and source logs and migration backups are untouched. The directory is outside all numeric Topic directories: existing navigation, migration and numeric ID allocation ignore it, while a later reuse of a numeric Topic ID still has a different generated Session identity.

`TopicIndex.finishDeleting()` publishes the completed receipt with the existing atomic JSON writer before removing the cleanup marker. Publication failure leaves that recovery marker in place. A crash between receipt publication and marker removal still reports pending cleanup until recovery finishes. Modern `storage: 'source'` records require their bound source root; an unavailable root raises an error rather than falling back to legacy storage. Only an actual legacy record can use its existing private legacy source-index directory when no source root is bound. The writer never creates a source Session or its Citer root.

`TopicIndex.findDeleted(sessionId)` returns an exact validated identity with `cleanup: 'pending' | 'complete'`, or `undefined` when no evidence exists. It merges matching committed recovery markers and durable receipts; a remaining marker takes precedence over a completed receipt, and conflicting source or numeric Topic identities raise an error. Legacy markers must match their base64url parent directory, modern markers must match the bound source, and each marker's Session header must identify the same Session. Receipt readers reject unknown schema fields, invalid generated Session identities, links, oversized files and mismatched source identities. Only `ENOENT` is treated as absence; malformed data and other I/O failures remain errors. Already completed deletions from older builds whose markers are gone are not reconstructed or guessed.

Validation: `pnpm typecheck` passed Host and Client against SDK 0.2.1-alpha.1; `pnpm typecheck:desktop` passed both faces against official Desktop SDK 0.2.0-rc.2. Focused source and note whitespace checks passed. Review confirmed that `reserve`, `all`, migration and deletion scans only use numeric Topic directories, so the separate receipt directory does not retain or reserve deleted numeric directories. No artificial model, fixture, temporary test script, production deletion, UI operation, build, package installation or commit was performed for this storage subtask. Installed-candidate tests must still verify local and other-window deletion, a pending submission, temporary connectivity failure and Host restart without source-log changes; this implementation alone does not establish functional acceptance or release readiness.
